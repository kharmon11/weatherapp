# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

WeatherApp is a full-stack weather application that shows current conditions and a 10-day forecast for a user-selected location (search by city, browser geolocation, or map click). It has a React/TypeScript frontend and a FastAPI backend; the backend geocodes the location via the Google Maps Geocoding API, then fetches weather from OpenWeatherMap's One Call API 4.0. It is live in production at https://weather.kenharmon.net.

## Tech stack

- **Frontend**: React 19, TypeScript, Vite 7, Sass, `@vis.gl/react-google-maps`, Recharts (forecast graphs), Axios, react-icons (one icon; the footer's GitHub mark is an inline SVG, `common/GithubIcon.tsx`). Package manager: pnpm (npm also works).
- **Backend**: Python 3.11, FastAPI, served via Uvicorn (dev) / Gunicorn+UvicornWorker (prod), httpx for outbound API calls, Pydantic Settings for config.
- **Deployment**: Google Cloud Run (Docker image built from `server/Dockerfile`), serving `weather.kenharmon.net` and `wx.kenharmon.net`. Deploys use an automated GitHub Actions pipeline (`.github/workflows/ci-cd.yml`) using Workload Identity Federation — see the Deployment section below and `DEPLOYMENT.md` for the full flow. (The app previously ran on App Engine; that deployment has been retired.)

## Common commands

### Frontend (run from `client/`)
- `pnpm run dev` — start Vite dev server at `http://localhost:5173`
- `pnpm run build` — type-checks (`tsc --noEmit` against both `tsconfig.app.json` and `tsconfig.node.json`), then `vite build`, then runs `copy-dist`. Fails fast on type errors before producing any output.
- `pnpm run copy-dist` — deletes `../server/app/dist` and copies the built `dist/` there (this is how the frontend gets served by FastAPI in prod)
- `pnpm run lint` — ESLint (flat config, `eslint.config.js`)
- `pnpm run preview` — preview the production build locally
- `pnpm test` — run the Vitest suite once (`client/src/**/*.test.{ts,tsx}`)
- `pnpm test:watch` — Vitest in watch mode
- `pnpm test:coverage` — Vitest once with a coverage report (v8 provider, configured in `vite.config.ts`'s `test.coverage` block). The terminal table hides fully-covered files by default (`skipFull`) so it only lists files needing attention; a full per-file report is written to `client/coverage/index.html`.

### Backend (run from `server/`, with venv active)
- `uvicorn app.main:app --reload` — dev server at `http://localhost:8000`
- `gunicorn -w 2 -k uvicorn.workers.UvicornWorker app.main:app` — prod entrypoint (matches the `server/Dockerfile` `CMD`, which also binds `-b :$PORT` for Cloud Run)
- `pip install -r requirements.txt -r requirements-dev.txt` — install prod + test deps (test deps are split into `requirements-dev.txt` so they don't ship to prod)
- `pytest` — run the backend test suite (`server/tests/`, config in `server/pytest.ini`). No Python linter is configured.
- `pytest --cov=app --cov-report=term-missing` — run tests with a coverage report (`pytest-cov`, already in `requirements-dev.txt`), showing uncovered line numbers per file.

### Structure doc
- `scripts/generate-structure.sh` regenerates the file tree block in `README.md` (between `<!-- START STRUCTURE -->`/`<!-- END STRUCTURE -->`). Requires `tree`.

There is no root-level build tooling — the root `pnpm-lock.yaml`/`requirements.txt` are legacy/unused leftovers with no corresponding `package.json` to drive them; always `cd client` or `cd server` first.

## Architecture notes

- **`server/app/main.py`** — FastAPI app entrypoint. CORS origins come from `ALLOWED_ORIGINS` env var in production, hardcoded localhost otherwise. When `ENV=production`, it additionally serves the built frontend as static files (mounted at `/`) plus an explicit `no-cache` route for `index.html` (for cache-busting on deploys). In dev, only the API runs — the frontend is served separately by Vite. `GZipMiddleware` (level 5, 1 KB minimum) compresses every response, and the static mount is a `HashedAssetStaticFiles` subclass that adds `Cache-Control: public, max-age=31536000, immutable` to 200/304 responses under `assets/` only (Vite content-hashes those filenames; `index.html` keeps its `no-cache` route, so deploys are still picked up immediately). It also sets the `httpx` logger to WARNING: httpx logs full request URLs at INFO and our Google/OpenWeatherMap URLs carry the API keys as query params — don't lower that level. The frontend calls the API same-origin in every deployed environment (see `weatherService.ts` below), so CORS only ever needs to cover browsers on the known custom domains in `ALLOWED_ORIGINS` — it does not need to (and can't practically) special-case the ephemeral non-promoted-deploy hostname, which changes every deploy.
- **`server/app/api/openweathermap.py`** — the only API route, `GET /api/openweathermap?location=`. `location` is either a free-text address or a `"lat,lon"` pair; it's passed to `geocode()` unchanged either way — Google's Geocoding API accepts and reverse-geocodes a coordinate pair given as a plain address string, so no branching is needed. Flow: geocode → fetch weather → merge and return.
- **`server/app/services/geocode.py`** and **`services/openweathermap.py`** — thin async wrappers around the Google Geocoding API and OpenWeatherMap One Call API respectively, using `httpx`. One Call 4.0 is split into 6 modular endpoints; the weather service concurrently calls the only 3 the frontend consumes (`current`, `timeline/1min`, `timeline/1day` — `hourly` and alert detail are unused) via `asyncio.gather` and reassembles them into the same `{lat, lon, timezone, timezone_offset, current, daily, minutely}` shape the frontend expects. Each of the 3 calls independently retries on timeout (3 attempts, backoff) and translates upstream failures into `HTTPException`s with `{error_type, message}` detail payloads — the frontend depends on this shape; a failure in any one of the 3 calls fails the whole request, and the other in-flight calls are cancelled (no backoff sleep follows the final failed attempt). Non-JSON upstream bodies, and Google network errors, become `502`s with the same error shapes instead of unhandled 500s. **Both services cache successful results in memory** (`core/cache.py`): geocode by normalized address for 24 h (raw `"lat,lon"` inputs bypass it, since they never repeat); weather per endpoint, keyed on coordinates rounded to 3 decimals (~110 m, matching OpenWeather's advertised resolution), with TTLs of 2 min (`1min`), 5 min (`current`), 10 min (`1day`) — OpenWeatherMap documents a ~10 min refresh for the product as a whole and no per-endpoint schedule. Errors are never cached. Caches are per-process (each gunicorn worker has its own; they start empty on cold start), bounded (LRU), and their values are shared between callers — treat them as read-only. The three calls can therefore come from different moments (up to a few minutes apart).
- **`server/app/core/cache.py`** — `TTLCache`: small in-memory TTL + LRU cache (injectable clock for tests, no dependency). Used by both services.
- **`server/app/core/config.py`** — Pydantic `Settings` pulling `GOOGLE_MAPS_GEOCODING_KEY` / `OPENWEATHERMAP_API_KEY` from env (`.env` via `python-dotenv` in dev, injected by Cloud Run from Secret Manager in prod).
- **`server/tests/`** — pytest suite covering `main.py` (CORS/static-mount branching by env, gzip, asset caching headers), the `/api/openweathermap` route, both service wrappers, and `Settings`. Outbound HTTP to Google/OpenWeatherMap is mocked with `respx` at the transport level (service-layer tests) or by patching the service functions directly (route-level tests) — no test ever makes a real API call. A `conftest.py` fixture stubs `settings` with dummy keys for every test, and another clears the module-level caches between tests (new module-level state in the services must be reset there too). `test_cache.py` covers `TTLCache` with a fake clock.
- **`client/src/hooks/useWeather.tsx`** — central state/data-fetching hook (weather data, loading, error state) used by `Body.tsx`; all three fetch triggers (form submit, geolocation, map click) funnel through `fetchWeather`. Only the most recent request may update state: each takes a new id from a ref and aborts the previous request's `AbortController`; results, errors and the loading flag from superseded requests are ignored (this also covers a geolocation lookup, which can't be cancelled, resolving after a newer search). Unmounting aborts anything in flight. Geolocation uses `{enableHighAccuracy: false, timeout: 20 s, maximumAge: 5 min}`.
- **`client/src/services/weatherService.ts`** — the single Axios call to the backend (30 s timeout, accepts an `AbortSignal`); normalizes Axios errors into `{error_type, message}` objects consumed by `useWeather` — a canceled request becomes `{error_type: "canceled"}`, which `useWeather` discards. `VITE_API_BASE_URL` is empty in every deployed build (an intentional value, not a missing one — see `validateEnv.ts`), so the request is always same-origin relative to whatever hostname served the page; FastAPI always serves the frontend and API from the same origin (see `main.py` above), so this works identically for the promoted domain, any other custom domain pointed at the app, and non-promoted candidate deploys alike. Only local dev sets it to an absolute `http://localhost:8000`, since Vite and FastAPI run as separate servers there. `pnpm run preview`'s proxy config (`vite.config.ts`) forwards `/api` to a locally-running backend so the same-origin call still resolves when previewing a production build locally.
- **`client/src/components/Body/`** — main UI: `LocationForm` (search/geolocation), `Current` + `GoogleMap` + `WindVane` + `MinutelyChart` (current conditions), `WeekForecast/` (`DailyForecasts` list + `WeekGraphs` temp/wind charts via Recharts). `Current` and `WeekForecast` are lazy-loaded (`React.lazy`) to keep the initial bundle small, and `Body` starts importing both as soon as a request begins so the chunks download in parallel with the API call. Recharts is the largest chunk, so it is loaded on demand: `MinutelyChart` is lazy inside `Current` (only fetched when precipitation is forecast), and `WeekGraphs` is mounted on the first click of the Graphs tab (hovering the tab prefetches the chunk); once opened it stays mounted and tab switches only swap CSS classes (tab state is React state in `WeekForecast`). `GoogleMap` must **not** be given a `key` derived from the location: the `<Map>` is uncontrolled (`defaultCenter` only applies at creation), and a small `Recenter` child calls `map.panTo()` on location changes so the map instance — and the billable map load — is reused and the user's zoom/pan is kept.
- Frontend/backend are coupled by the `copy-dist` step: the client build output must land at `server/app/dist` for the FastAPI prod server to find and serve it.
- **`.github/workflows/ci-cd.yml`** — the CI/CD pipeline: runs backend/frontend test suites on every push and PR; on push to `master`, the `deploy-cloud-run` job builds the Docker image, pushes it to Artifact Registry, deploys it to Cloud Run as a no-traffic tagged revision, smoke-tests it, and only then shifts live traffic to it. See `DEPLOYMENT.md` for the full walkthrough.
- **`server/Dockerfile`** + root **`.dockerignore`** — container build for the live Cloud Run deployment. Two stages: Node builds `client/` (the `VITE_*` values come in as build args), then `python:3.11-slim` runs gunicorn+uvicorn and serves the built `dist` from `app/dist`. Build with the repo root as the context: `docker build -f server/Dockerfile .`. Targets `linux/amd64`. The `ci-cd.yml` `deploy-cloud-run` job builds, pushes, deploys a no-traffic tagged revision, smoke-tests it, then promotes; See the Cloud Run section of `DEPLOYMENT.md`.
- **`client/scripts/smoke-test.mjs`** — headless-Chromium script the deploy job runs against each freshly-deployed, not-yet-promoted version. Submits a real search ("Boston, MA") through `#location-input`/`#location-submit` and waits for `.location-name` to render, exercising the real Geocoding → OpenWeatherMap → frontend round trip. Fails (and blocks promotion) on an uncaught JS exception, any unexpected console error, a missing search form, or a missing/mismatched weather result. **Known, accepted gap: it does not verify the Google Map renders.** Requests to `maps.googleapis.com` are intercepted and fulfilled with an empty response before the page loads, so the real Maps script is never actually called. This isn't a workaround for one specific error — the real script can't reliably load in any headless CI browser at all, for two separate, unrelated reasons we hit and confirmed: its HTTP-referrer restriction can't cover the ephemeral per-deploy hostname (Google doesn't support wildcarding mid-label), and separately, GitHub's runners have no GPU, so the WebGL-dependent vector-tile rendering Maps needs also fails there. Chasing whatever error message Google's script produces next would just be the same fragile pattern a third time, so this excludes it from the test's scope entirely instead. Real users never hit this path — they load the real script from the promoted custom domain, which the Maps key's referrer restriction already allows and which has a real GPU.

## Deployment

- Deploys are automated via `.github/workflows/ci-cd.yml` (GitHub Actions) — see `DEPLOYMENT.md` for the full pipeline walkthrough, the required GitHub secrets/variables, and the rollback procedure. There is no routine manual deploy step anymore.
- Target: **Google Cloud Run** (service `weatherapp`, region `us-central1`). The runtime configuration (env vars, secrets, scaling limits) lives in the `gcloud run deploy` flags in `ci-cd.yml`; the two API keys come from Secret Manager.
- Both `.env` files (`client/.env*`, `server/.env`) are gitignored — they exist locally with real secrets in them but are **not** committed. Never add or force-commit them. A leftover local `server/app.yaml` from the App Engine era also holds real keys in plaintext: delete it, and never print or commit it.
- Every push to `master` triggers a deploy attempt: the pipeline builds and pushes the image, deploys it as a no-traffic revision tagged `candidate`, runs `client/scripts/smoke-test.mjs` against the candidate's own URL, and only shifts live traffic to it (`gcloud run services update-traffic ... --to-latest`) if the smoke test passes. A failed smoke test leaves the previously-live revision serving all traffic, untouched — the deploy job just ends red. Old container images are not deleted by the pipeline; keep an Artifact Registry cleanup policy on the `weatherapp` repository (see `DEPLOYMENT.md`).
- Known production origins configured in `ALLOWED_ORIGINS`: `weather.kenharmon.net`, `wx.kenharmon.net`, plus staging domains (`staging.kenharmon.net` and a separate `staging-*.appspot.com` project). Entries for the retired App Engine `appspot.com` URL are obsolete and can be removed from the GitHub variable. The candidate revision's hostname doesn't need an entry — the frontend never calls it cross-origin (see the `weatherService.ts` note above).

## Conventions

- Backend Python: 2-space indentation in `main.py`, `core/*.py`, and `api/openweathermap.py`; 4-space indentation in `services/*.py`. Match whichever file you're editing rather than reformatting.
- Backend errors are raised as `HTTPException(status_code=..., detail={"error_type": ..., "message": ...})` (or a plain string for generic 500s) — keep this shape since the frontend pattern-matches on `error_type`/`message`.
- Frontend: 4-space indentation, function components, `.tsx`/`.ts` with explicit `type`-only imports (`import type {...}`), hooks in `src/hooks/`, one-off helpers in `src/utils/`, Axios types in `src/types/`. Sass files live alongside their component (`Component.tsx` + `Component.sass`).
- Backend has a pytest suite (`server/tests/`, see Architecture notes) — run it after backend changes.
- Frontend has a Vitest + React Testing Library suite, config lives in `vite.config.ts`'s `test` block (`environment: 'jsdom'`, `setupFiles: './src/test/setup.ts'`). Tests are colocated with source (`Component.test.tsx` next to `Component.tsx`, same pattern as `.sass` files). No `globals: true` — import `describe`/`it`/`expect`/`vi` explicitly from `vitest` in each file, matching this repo's explicit-import convention. Axios, `navigator.geolocation`, and `recharts` are mocked at their boundaries in tests, since none of them work for real in jsdom. Run `pnpm test` after frontend changes. A few tests (`Body`, `Current`, `WeekForecast`) count dynamic-`import()` module loads with `vi.hoisted` counters inside `vi.mock` factories to prove chunks load lazily; a module stays loaded once imported within a file, so those tests must stay ahead of any test that renders the lazy component (each has a comment saying so), and the test file must not import the lazy module itself.
- The `README.md` project-structure block is generated, not hand-edited — update it via `scripts/generate-structure.sh`, not by hand.

## Things to be careful with

- **This is a live production app** at weather.kenharmon.net (Cloud Run). Merging any PR into `master` triggers a real deploy attempt via the automated pipeline — treat that merge, plus editing `.github/workflows/ci-cd.yml`, as high-impact and confirm with the user first. The deploy job's build-and-deploy-candidate steps run unconditionally on every `master` push (no path filtering is configured, so even doc-only changes trigger a real, harmless deploy attempt); a failed smoke test blocks promotion automatically, but doesn't stop the attempt itself from happening.
- `pnpm run build` type-checks before bundling — a build cannot "succeed" with type errors present.
- Changing the `/api/openweathermap` response shape or the `{error_type, message}` error shape requires updating `weatherService.ts`/`useWeather.tsx` in lockstep — they're tightly coupled to it.
- `ALLOWED_ORIGINS` is required and validated at startup in production (`main.py` raises if unset/empty) — don't remove that check.
